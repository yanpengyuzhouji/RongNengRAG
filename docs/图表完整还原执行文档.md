## 1. 总体方案

采用“结构化 HTML + 原始视觉资源叠加”的混合预览：

```text
PDF 页面

  → 8001 Pipeline 返回文字、表格、公式和视觉块 bbox
```

图题 `figure_title` 继续作为文字块渲染；图表视觉块只负责补回曲线、坐标轴、箭头和图片内容。

## 4. 设计约束

- 不改变文本入库、chunk、Embedding、Milvus 和章节目录逻辑。
- 不把 OCR 返回的 HTML/URL 直接当作可信资源。
- 页面图像必须来自同一次 OCR 请求，禁止使用不同 DPI 的二次截图。
- 图表裁剪失败时优雅降级为现有结构化文本预览。
- 大图资源要限制尺寸和数量，避免接口响应过大。

## 5. 后续增强

- 将 data URI 迁移为认证资源接口，减少大 PDF 的 HTML 响应体积。

### 6.2 数据流

```text
GET /files/{id}/content?editable=true
  → 同一版面渲染器增加原位编辑控件
  → iframe postMessage 上报 page_num + source block_index + 修改内容
  → 前端汇总修改并携带 base_revision
  → PUT /files/{id}/content
      ├─ 校验 revision 和版面块
      ├─ 应用文字修改/图片删除
      ├─ 图片删除时同步移除图内被遮盖 OCR 子块
      ├─ 从编辑后的 layout 重建逐页文本与 chunks
      ├─ Embedding + Milvus staging generation 校验
      ├─ 原子切换 active alias
      ├─ 发布 *.layout.json 和 *.layout.edited.json
      └─ 更新 file_registry 的 chunks/字符数/耗时
```

原始 PDF/PNG 文件保持只读；“写入”指发布编辑后的版面事实库、图表资源缓存和向量索引。预览、目录和向量文本都从同一编辑版 layout 派生。

### 6.3 一致性与失败保护

- `layout_revision` 是版面 JSON 的稳定 SHA-256；保存前再次校验，版本不一致时拒绝覆盖。
- Milvus 仍采用影子集合，当前文件的新 chunks 校验通过后才切换正式别名。
- 新版 layout 先写 pending 文件；向量、主 layout、编辑版 sidecar 和注册表完成后才算保存成功。
- 发布过程中发生异常会切回旧 Milvus generation，并恢复旧 layout/sidecar。
- 图片删除不仅删除 `visual_data_uri` 所在视觉块，也删除其 bbox 内被图片遮盖的 OCR 子块；图题位于图片外，默认保留。

## 7. 当前检索说明（2026-08-13）

图表预览资源与检索向量仍然解耦：调用 `rebuild-preview-assets` 只改 layout cache，不会修改 dense/sparse/BM25 索引。正常上传、编辑保存或 reindex 时，编辑版 layout 生成的文本会同时写入 Qwen dense vector 和本地 CPU BGE-M3 sparse vector；查询阶段再融合语料 BM25，并由本地 CPU BGE-Reranker-v2-m3 重排。若是升级前建立的旧库，使用 [`../scripts/rebuild_sparse_vectors.py`](../scripts/rebuild_sparse_vectors.py) 只迁移 sparse 字段，不影响图表缓存和原 dense 向量。
